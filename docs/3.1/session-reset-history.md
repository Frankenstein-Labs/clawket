# Acknowledged session Reset history

The Android QA management conversation confirmed a client defect: Reset succeeded in the backend and archived its old native thread, but the still-mounted Thread showed the old question and reply. Re-entering the conversation cleared them, and its explicitly saved local copy remained intact. This proves stale in-place presentation; it does not prove persistent cache corruption.

Session Panel actions run at the App root. `resetSessionHistory` captures local consumers on the exact adapter before the one reset dispatch. Only its successful acknowledgement retires the captured view. `useChatHistoryState` reuses selection retirement for the same key: invalidates requests/cache hydration, clears native cursor and local older segments, resets activity and loaded state, then reads a new head. It does not infer reset from missing native identity or an ordinary refresh. A new optimistic message submitted after the ACK still uses normal preservation.

Consumers check their original adapter, Agent/key and selection lifetime, including same-batch leaving and returning to the same key. The coordinator checks all captured consumers before synchronously retiring any epoch, so history retirement cannot invalidate the controller in that same acknowledged action. Controller retirement clears run presentation/timers and holds queued unsent input without clearing the composer or attachments. Auto-cache cancels its pending debounce synchronously before exact logical-session cache deletion. Already-dispatched cache saves precede deletion on the existing serialized index lock. Explicit Saved conversations use a separate store and remain untouched.

Rejection leaves the current history/cache intact. A failed new head read retains the now-empty acknowledged timeline and its normal manual refresh path; it cannot revive a pre-reset read. If cache deletion also fails, the retired selection continues blocking cache hydration until that selection retires; the backend ACK still succeeds and cannot invite a second Reset. No reset or send is retried automatically. OpenClaw/Hermes ordinary refresh retains its existing preservation semantics.

Verification: three real history-hook cases fail with the original consumer and pass with the fix (same-key ACK, delayed history/cache, failed new read); rejection, late scope and ordinary OpenClaw/Hermes reads remain compatible. The real history/controller successful-ACK ordering case and failed-delete/failed-head hydration case each fail before their corresponding hardening and pass afterward. Root's combined candidate passes six serial files: history 177, controller 96, auto-cache 3, cache storage 46, adapter events 48 and queue 112 (482 cases), plus Mobile typecheck. No full local suite is run.

Physical Android acceptance on the combined `74f696bd` candidate passes with a fresh, separately identified QA conversation. Its one initialization Send produces one receipt/start/completion/user/reply and zero tools, errors or aborts. After one successful Reset, the still-mounted screen is empty while its verified unsent text draft remains; a settled screenshot after leaving and re-entering confirms both states. Read-only host evidence confirms the old Native thread is archived with unchanged complete history bytes and the same sole receipt. Re-entry may prepare a different empty Native binding; absence of a binding is not required after re-entry. The original explicitly saved QA copy remains readable with its question and reply.
